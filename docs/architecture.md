# Architecture notes

## `global-error.tsx`'s home link

`app/global-error.tsx` replaces the root layout when it renders, so
`next/link`'s router context is not guaranteed to be mounted. The home link
uses a plain `<a>`, which forces a full navigation instead of depending on
that context. `eslint.config.mjs` disables `@next/next/no-html-link-for-pages`
for this file for that reason.

## Blog posts: citations

A post is a hand-authored React Server Component at `app/blog/<slug>/page.tsx`
and is registered in `lib/blog/posts.ts` (a post that exists only on disk is
unreachable from `/blog`). There is no Markdown/MDX layer; citations do not
need one.

`lib/blog/posts.ts`'s `BLOG_POSTS_PER_PAGE` (15) splits the registered posts,
newest first, across page 1 at `/blog` and further pages at `/blog/page/<n>`,
statically generated by `app/blog/page/[page]/page.tsx` from
`generateStaticParams`; a page number outside that range 404s rather than
rendering empty. `lib/site/navigation.ts` recognizes the `/blog/page/<n>`
shape separately, in its own `blogPageNumberFromParts`, to build the
breadcrumb — the two are not the same code path, so a change to one route
shape without the other leaves the breadcrumb wrong while the page itself
still renders.

Citations are numbered brackets in first-appearance order, `[n]`, each linked
to a `<li id="ref-<id>">` in a trailing `<References>` list, with one
back-link anchor per occurrence for a source cited more than once. The
`Reference` type is shared, from `lib/blog/bibliography.tsx`; the data is
not — each post declares its own `references` array next to the prose that
cites it. The numbering registry (see `app/blog/tickerbox-cli/citations.tsx`)
is built once per render and passed explicitly to `Cite`/`References`, never
held in module-level state, so citation numbers cannot leak or collide
between posts or across a dev-mode re-render; each post that cites a source
carries its own copy of this registry module rather than importing a shared
one. A back-link anchor for a source cited only once still needs a distinct
accessible name (an `aria-label` naming which citation it returns to): a bare
`^` glyph as the only accessible name is indistinguishable, to assistive tech,
from every other once-cited source's back-link on the same page.

## The `/blog/page/[page]` route template stays in the build manifest at any post count

`tests/unit/route-inventory.build-output.test.ts` expects
`.next/prerender-manifest.json`'s `dynamicRoutes` to carry exactly
`/blog/page/[page]`, unconditionally — not only when `blogPageCount()`
produces a second page. `generateStaticParams` can return zero params (one
post, so nothing past page 1) and the manifest still lists the template,
with `fallback: false`, because the route exists as a file on disk
(`app/blog/page/[page]/page.tsx`) independent of how many params were
generated for it; Next.js registers the template at build time from the
route's file-system shape, not from its param count. A derivation that
instead expects the template to disappear once there is nothing to
paginate is checking Next.js's behavior against a guess rather than the
manifest it writes.

## No-JS content test coverage

These tests cover no-JS rendering, each a different route, layer, or method:

- `app/layout.nojs.test.tsx` renders `RootLayout` directly with jsdom and
  asserts it emits no analytics or speed-insights script reference, even
  under `NODE_ENV=production`. It covers the layout, not any one page.
- `app/page.nojs.test.tsx` renders `app/page.tsx` (home) directly with jsdom
  and asserts its critical text and links survive with no script running.
- `app/canary/page.nojs.test.tsx` renders `app/canary/page.tsx` directly
  with jsdom the same way, and asserts every copy button is gated behind
  `js-only`.
- `tests/unit/nojs-content-home.build-output.test.ts` asserts against the
  built `/` output (`.next/server/app/index.html`) instead of a jsdom
  render, so it catches anything the build pipeline changes that a direct
  render would not.
- `tests/unit/nojs-content.build-output.test.ts` asserts against the built
  `/canary` output (`.next/server/app/canary.html`) the same way.
- `tests/unit/nojs-content-blog.build-output.test.ts` asserts against the
  built `/blog` and `/blog/tickerbox-cli` output the same way.
- `app/blog/verify-posts/page.nojs.test.tsx` and
  `tests/unit/nojs-content-verify-posts.build-output.test.ts` cover
  `/blog/verify-posts` both ways.

The build-output test is the binding one: it reads the HTML the site
serves, so it covers whatever a direct render would and whatever
the build pipeline does afterwards. A jsdom render test adds faster
feedback and names which component broke, not coverage. A route needs the
build-output half. The jsdom half is optional: `/blog/verify-posts` has one
and the other blog routes do without.

What a route's no-JS test must assert is not only that the content is
present. Any control that needs JavaScript has to be gated behind
`js-only`, or a reader without JavaScript is shown a control that cannot
work. Assert that gating by counting it against the controls the page
rendered, never against a fixed number: a count written down goes
stale the moment a page gains a control, and goes stale silently.

Both build-output tests strip React's empty streaming-SSR boundary markers
(`<div hidden="">` wrapping `<!--$-->`/`<!--/$-->`) before asserting no
hidden content leaked into the no-JS output. React emits one of these for
every Suspense boundary regardless of whether it suspended. It carries no
page content, so it is removed the same way a `<script>` tag is, rather than
treated as hidden content.

## Navigation is a hand-maintained switch

`lib/site/navigation.ts`'s `entriesFor()` is a `switch` over route strings
that `SiteBar` renders as a filesystem-style directory listing. Nothing
generates this list from the route tree: a new top-level route gets no entry
in its parent's listing until this switch is edited by hand, and nothing
fails a build for forgetting.

`SiteBar` (`components/site-bar.tsx`) has a fixed rendered shape that any
change to it must preserve: the full path on the left, with every ancestor
segment but the current page linked back to its own route; the current
route's `entriesFor()` listing on the right; and a back control to the
parent route, present everywhere except at `/`, where there is no parent to
go back to. The canary page's published-files listing is not a separate
component — it is the `/canary` case of `entriesFor()`, rendered through
this same bar.

`SiteFooter` (`components/site-footer.tsx`) is the one footer in the app,
rendered on every route (home, canary, privacy, every blog post and the
blog index). It replaced a canary-specific footer; a page that needs
different footer content is a change to `SiteFooter` itself, not a reason
to reintroduce a second footer component.

## Blog client components

Blog content renders on the server. `components/blog/post-read-marker.tsx`
tracks a post read when an `IntersectionObserver` sees its target, and
`components/blog/citation-link.tsx` tracks citation clicks. Command and copy
adapters render shared interactive components; `lib/copy-text.ts` records
successful copies through the package callback.

These events call `@vercel/analytics`'s `track()` outside the production gate
around the page-view and vitals collectors in `app/layout.tsx`. Client behavior
must remain usable with JavaScript disabled; copy controls hide themselves in
that case.

## A module used only by its own test passes the dead-code gate

`knip`'s vitest plugin treats every `*.test.{ts,tsx}` file as an entry point,
so a module imported solely by its own test file reads as used even when
nothing else in the app imports it. `bun run knip` (part of `just check`)
will not catch this. To check a module for real, search its imports outside
test files, for example:

```bash
rg --type ts -l "from ['\"].*/module-name['\"]" | rg -v '\.test\.'
```

An empty result means only the test imports it.

## `/feed.xml` is the one route handler, and needs its own static declaration

`app/feed.xml/route.ts` is the only `route.ts` in this codebase; every other
route uses a page, layout, or metadata-route file convention. Next 16 route
handlers default `GET` to dynamic (request-time) rendering, unlike the page
and metadata-route conventions used everywhere else in `app/`, so the
handler declares `export const dynamic = "force-static"` to opt back into
build-time rendering. Without it, the route is not prerendered and
`tests/unit/route-inventory.build-output.test.ts`'s
`compute: "static"` assertion fails the build. The handler reads no request
state (no `headers()`, `cookies()`, `searchParams`) — it computes the feed
once, at build time, from `postsByNewest(posts)`.

The feed carries title, link, and publication date only, for every post in
`lib/blog/posts.ts` — no summary and no full article content. `BlogPost` has
no description field, and `public/posts.asc` is a one-way hash manifest of
built article text, not a text source a feed builder could read back; a
full-content entry would be a second, unattested copy of post text with no
drift detection of its own, which `AGENTS.md` §7 already flags as a known
gap for the one copy that exists today. A short title-and-link entry creates
no second copy to drift.

`lib/feed/atom.ts`'s `buildAtomFeed` takes pre-shaped, already-absolute
entries and imports nothing from `lib/blog/posts.ts`; the route handler, not
the builder, does the `BlogPost`-to-entry translation. This keeps the
builder fixture-testable with literal input and keeps it from needing a
change whenever the post list's shape changes.

Autodiscovery is a hand-rendered `<link rel="alternate" type="application/atom+xml">`
in `app/layout.tsx`, not `lib/site/metadata.ts`'s `alternates.types` map.
Next's metadata merge replaces a route's `alternates` object wholesale
rather than deep-merging it with the parent layout's, and every page under
`app/blog/`, `app/privacy/`, and `app/canary/` already sets its own
`alternates: { canonical: "..." }` — a root-only `alternates.types` entry
would render on `/` only and be silently absent everywhere a reader is
reading a post. `app/layout.tsx` already renders hand-written
`<link rel="preload">` tags for fonts the same way, so a feed `<link>` there
is the same mechanism, not a new one.

## `published-files.test.ts` has no `published-files.ts`

`lib/publish/published-files.test.ts` predates the other generators in
`lib/publish/` (`email-signature.ts`, `llms-txt.ts`, `readme-badge.ts`,
`readme-proof-date.ts`, `security-policy.ts`, `security-txt.ts`, `wkd.ts`,
each with its own matching `.test.ts`). The
original `published-files.ts` generator it tested was deleted; the test
file was kept and repointed to import each surviving generator directly and
assert its output against the file committed under `public/`. A reader
expecting a one-to-one generator/test pairing for every file in the
directory will not find one for this name — the test is real and still
runs, no longer paired with a file of its own name.
